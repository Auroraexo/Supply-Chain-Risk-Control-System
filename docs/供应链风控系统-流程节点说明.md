## 二、主链路节点说明（请求接入 → 自动决策）

### N1 · 开始
- **位置**：流程入口。
- **触发方**：外部业务系统或前端，针对一条已入库的 `RawData` 发起风险评估。

### N2 · 数据输入：POST /risk/analyze
- **核心功能**：接收 `raw_data_id`，进入风险评估服务。
- **前置权限**：登录用户（JWT）。批量入口为 `/risk/analyze/batch`。
- **配套**：300 秒整体超时（`asyncio.timeout(300)`），超时返回 `504 AGENT_TIMEOUT`。

### D1 · Redis 分布式锁
- **判断条件**：`SET analysis-lock:{raw_data_id} token NX EX=330` 是否成功？
  - **否** → 返回 `409`：「该数据正在分析中，请稍后查询结果」（结束）。
  - **是** → 继续。
- **锁释放**：流程 `finally` 中通过 Lua 脚本「比对 token 后再 DEL」，避免误删他人锁。

### D2 · 缓存命中检查
- **判断条件**：未强制重分析（`force_reanalyze=false`）且该 `raw_data_id` 已存在 `AnalysisResult`？
  - **是** → 直接读取已有结果返回，标记 `from_cache=true`，不重跑 Agent。
  - **否** → 继续。

### D3 · 原始数据存在性
- **判断条件**：根据 `raw_data_id` 查询 `RawData` 记录？
  - **不存在** → `404 NotFoundException`。
  - **存在** → 继续。

### D4 · 数据有效性
- **判断条件**：`raw_data.status == RawDataStatus.INVALID`？
  - **是** → `422 DataQualityException`（数据已被标记为无效）。
  - **否** → 继续，解析 payload（JSON 解析失败时降级为前 500 字字符串，不中断流程）。

---

### N5 · Scout Agent（数据采集与质检）
- **核心功能**：
  1. 取数：优先使用注入的 `raw_data_payload`，否则通过 `get_raw_data` 工具回查。
  2. 结构化事实：输出 `structured_facts`。
  3. 数据质量检查：调用 `check_data_quality` 输出 `quality_score` 与 `missing_fields`。
  4. 用 LLM 生成数据质量说明（失败时静默回退到规则文本，**不影响确定性评分**）。
- **异常处理**：节点内部异常时 `retry_count += 1`；累计 `retry_count > 2` 时置 `status=FAILED`。

### D5 · Scout 后路由（`should_continue_after_scout`）
按顺序判断，任一命中即路由：
1. `status == FAILED` → **human_review**。
2. `data_quality_score < 0.5` → **human_review**。
3. `retry_count > 2` → **human_review**。
4. 否则 → **analyst**。

---

### N6 · Analyst Agent（风险评分）
- **核心功能**：
  1. 容错提取参数：`delay_days`、`price_deviation`、`supplier_rating`（钳制 0–5）、`historical_incidents`；非法值回退默认。
  2. 通过 `query_historical_patterns` 查询相似历史风险，得到 `similarity_score`。
  3. `calculate_risk_score` 算原始分；历史相似度按 `similarity × 20` 加权上调（封顶 100）。
  4. **等级映射**：
     - `> 70` → critical
     - `> 50` → high
     - `> 30` → medium
     - `≤ 30` → low
  5. 异常标签：`delay`（delay_days>0）、`price_anomaly`（price_deviation>15）、`supplier_risk`（rating<3.0）、`historical_pattern`（命中历史）。
  6. LLM 生成分析推理（失败回退规则文本）。
- **异常处理**：节点内异常 `retry_count += 1`；`retry_count > 3` 时置 `status=FAILED`。

### D6 · Analyst 后路由（`should_continue_after_analyst`）
按顺序判断：
1. `status == FAILED` → **human_review**。
2. `retry_count > 3` → **human_review**。
3. `risk_level ∈ {high, critical}` → **reflection**（高风险二次校验）。
4. 否则（low / medium）→ **decider**。

---

### N7 · Reflection Agent（高风险二次校验）
- **触发条件**：仅当 Analyst 判定 high / critical 时进入。
- **核心校验**：
  1. **高风险低置信度**：`risk_score > 80` 且 `confidence < 0.7` → `passed=False`。
  2. **事实完整性**：`structured_facts` 为空 → `passed=False`。
  3. **标签一致性**：`delay` 标签但 `delay_days ≤ 0` → 仅记录建议（不直接判失败）。
- **异常处理**：节点自身抛异常时，兜底写入 `reflection_result.passed=False`。

### D7 · Reflection 后路由（`should_continue_after_reflection`）
- `passed == False` → **human_review**。
- `passed == True` → **decider**。

---

### N8 · Decider Agent（最终决策）
- **决策来源（优先级）**：
  1. **规则引擎**：`RuleLoader` 加载活跃 `RuleNode` 决策树，在 `{risk_score, risk_level, delay_days, price_deviation, supplier_rating, historical_incidents}` 上下文上求值；命中即返回。
  2. **矩阵兜底**：规则引擎未命中或异常时使用：
     | risk_score | action | confidence |
     | --- | --- | --- |
     | < 30 | approve | 0.95 |
     | 30 – 50 | approve | 0.80 |
     | 50 – 70 | escalate | 0.60 |
     | ≥ 70 | reject | 0.90 |
- **反思加权**：若 `reflection.passed == False`，`confidence -= 0.15`。
- **异常处理**：`retry_count > 3` → `status=FAILED`。
- **LLM 解释**：生成决策说明，失败回退规则文本。

### D8 · Decider 后路由（`should_continue_after_decider`）
- `status == FAILED` → **human_review**。
- 否则 → 流程结束，进入持久化。

---

### N9 · 结果持久化（事务提交）
- **写入内容**：
  1. `AnalysisResult`：risk_score / risk_level / anomaly_tags / reasoning / facts_summary（含 provenance：输入哈希、配置哈希、规则版本、prompt 哈希、节点耗时）。
  2. `DecisionResult`：若 `agent_status == HUMAN_REVIEW`，决策写为 `pending_review`；否则按 Agent 决策写 `approve / reject / escalate`。
  3. `RawData.status → PROCESSED`，回写 `quality_score`（Scout 异常时为 None，回退 0.0，**不伪造 0.95**）。
- **写入时机**：Agent 调用前先 `db.rollback()` 释放只读连接，避免长事务占连。

### D9 · 是否触发高风险通知
- **判断条件**：`agent_status == HUMAN_REVIEW` 或 `risk_level ∈ {high, critical}`？
  - **是** → 写一条 `NotificationOutbox`（异步通知泳道）。
  - **否** → 直接进入自动结束。
- **通知失败处理**：Outbox 写入异常仅 `warning`，不阻断主事务。

### N10 · 自动决策结束
- 输出最终决策：`approve` / `reject` / `escalate`，附带 confidence、decision_explanation、reflection_passed。

## 三、人工审核与风险处置闭环

### H0 · HumanReview 节点（流程挂起）
- **触发入口**：D5 / D6 / D7 / D8 任一异常或高置信风险路径。
- **核心动作**：
  - 汇总触发来源（agent_failure / low_quality / retry_exhausted / reflection_failed）。
  - `state.status = HUMAN_REVIEW`，`decision = pending_review`。
  - 写 Agent 执行日志。
- **流程挂起**：LangGraph 至此 END，等待人通过 API 处理。

### H1 · 待审列表
- **接口**：`GET /review/pending`（分页）。
- **角色**：`decider` / `admin`。

### H2 · 人工审核动作判断
仅 `pending_review` 或 `escalate` 状态可被审核；其他状态返回 `409 已审核`。

| 动作 | 接口 | 校验规则 | 结果 |
| --- | --- | --- | --- |
| approve | `POST /review/{id}/approve` | 直接通过 | `decision → approve` |
| reject | `POST /review/{id}/reject` | **必须填写理由** | `decision → reject` |
| override | `POST /review/{id}/override` | **必须填写理由** 且 `override_decision ∈ {approve, reject, escalate}` | `decision → override_decision` |

### H3 · 不可变审计
- 每次审核写一条 `AuditEvent`（action=`review.{approve|reject|override}`），含 before / after / comment / reviewer，`revision += 1`。
- 人工审核通过**不会**改写模型原始置信度。

### H4 · 风险处置状态机（case_status）
合法迁移：

```
open ──→ in_progress ──→ resolved ──→ closed
 ↑                                  │
 └─────────────── 仅 admin ─────────┘
```

| 当前状态 | 允许迁移到 |
| --- | --- |
| open | open, in_progress |
| in_progress | in_progress, resolved |
| resolved | in_progress, resolved, closed |
| closed | open（仅 admin） |

**强校验规则**：
- 目标状态不在合法迁移表内 → `422 不允许跳过处置或复核步骤`。
- `revision` 不匹配 → `409 任务已更新，请刷新后重试`（乐观锁）。
- `closed` 状态要重新打开 → 仅 `admin`。
- 若当前决策仍是 `pending_review` 或 `escalate`，**不允许直接 closed**（须先完成审核）。
- 目标状态 ≠ open 时，必须指定 `owner_id` 和 `due_at`；负责人不存在或已禁用 → `422`。
- 目标状态为 `resolved` 或 `closed` 时，必须填写 `resolution`（整改结果及证据）。
- 每次更新写 `AuditEvent(action=treatment.update)`。

### H5 · 风险闭环关闭
- 所有处置审计可通过 `GET /decision/{id}/history` 回溯；`GET /audit`（admin）查看全量审计事件。

## 四、异步通知投递链路

### N11 · NotificationOutbox（DB）
- 主事务内写入，保证「业务落库」与「待发通知」原子提交。
- 字段：`level`、`payload{type, request_id, risk_score, details}`、`status=pending`、`attempts=0`。

### N12 · Worker 轮询（`app/workers/notifications.py`）
- 每 10 秒扫描 `status=pending`，`FOR UPDATE SKIP LOCKED` 加行锁，每次最多 20 条。
- 发布到 RabbitMQ 后置 `status=published`；发布异常 `attempts += 1`，**累计 ≥ 5 次置 `failed`**。

### N13 · RabbitMQ
- 队列：`risk_alert.high.v2` / `risk_alert.normal.v2`，持久化消息。
- 失败重试队列：`risk_alert.{group}.retry.v2`。

### N14 · Consumer 投递
- Redis 锁 `notification-lock:{message_id}`（120s）防重复消费。
- 按 `notifications.channels` 配置遍历启用渠道：
  - **email**：SMTP + STARTTLS。
  - **webhook**：POST JSON，带 `Idempotency-Key`。
  - **slack**：POST `{text}` 文本。
- **渠道级去重**：Redis 键 `notification:{event_id}:{channel_id}`，TTL 7 天。
- 投递成功写 `AuditEvent(action=notification.delivered)`。
- **失败处理**：
  - `attempts < 3` → 转发到重试队列并 ack。
  - `attempts ≥ 3` → `reject(requeue=False)` 进入死信。

## 五、关键设计要点速查

| 关注点 | 实现 |
| --- | --- |
| 全链路追踪 | 每次评估生成 `request_id`，贯穿 Analysis / Decision / Agent 日志 / AuditEvent / 通知事件 |
| 并发安全 | Redis 分析锁（330s）+ Outbox 行锁 SKIP LOCKED + 处置 `revision` 乐观锁 |
| LLM 失败兜底 | Scout / Analyst / Reflection / Decider 中 LLM 调用异常均回退规则文本，**评分与决策不依赖 LLM** |
| 高风险二次确认 | high/critical 必经 Reflection；不通过转人工 |
| 规则可演进 | `RuleNode` 决策树 + `RuleVersion` 快照；运行时记录 `active_rule_versions_at_start` 与 `configuration_hash` |
| 审计不可篡改 | 审核、人工覆盖、处置更新、通知投递全部写入 `AuditEvent`，只增不改 |
| 投递可靠性 | Outbox 模式 + at-least-once + 渠道去重 + 有限重试 + 死信队列 |
| 失败超时 | 整体 300s 超时；节点级失败重试（Scout >2、Analyst/Decider >3）后转人工 |

## 六、异常与出口对照

| 异常出口 | HTTP 状态 | 触发条件 |
| --- | --- | --- |
| 正在分析中 | 409 | Redis 锁未抢到 |
| 缓存命中 | 200 | 已有分析结果且非强制重跑 |
| 数据不存在 | 404 | `raw_data_id` 查无记录 |
| 数据无效 | 422 | `RawData.status = INVALID` |
| 分析超时 | 504 | 整体超过 300 秒 |
| Agent 空结果 | 500 | `run_decision_flow` 返回 None |
| 已审核 | 409 | 对非 pending/escalate 记录再次提交审核 |
| 跳步处置 | 422 | 状态迁移不在 TRANSITIONS 表内 |
| 关闭前未审核 | 422 | 当前决策仍为 pending_review / escalate |
| 重开已关闭 | 403 | 非 admin 尝试 closed → open |
